# Code Quality Guide

이 문서는 React + TypeScript 작업에서 팀이 같은 기준으로 리뷰하기 위한 최소 규칙입니다.
목표는 멋진 추상화가 아니라 팀원이 빠르게 이해하고 안전하게 수정할 수 있는 코드입니다.

## Priority

- 기준이 충돌하면 팀원이 빠르게 이해하고 안전하게 수정할 수 있는지를 먼저 봅니다.
- 기본 우선순위는 핵심 흐름을 위에서 아래로 읽게 두는 것입니다.
- 공통화 때문에 파일, 함수, 조건을 계속 오가야 한다면 공통화를 보류하고 중복을 허용합니다.
- 보안, 인증, 권한, 결제처럼 변경 위험이 큰 영역은 예외적으로 응집도를 우선할 수 있으며, PR에 근거를 남깁니다.

## Readability

- R1. 한 덩어리에서는 한 맥락만 다룹니다.
- 동시에 실행되지 않는 권한, 상태, 모드 분기가 많으면 케이스 컴포넌트나 작은 하위 컴포넌트로 분리합니다.
- if, ternary, switch가 UI와 로직 전반에 흩어지면 케이스 컴포넌트로 쪼갭니다.
- R2. 페이지와 상위 컴포넌트에는 의도와 화면 흐름이 먼저 보이게 둡니다.
- 로그인 체크, 리다이렉트, 권한 확인, 쿼리 파라미터 해석 같은 부가 로직은 필요한 경우 custom hook이나 wrapper로 격리합니다.
- R3. 상태, API, 타이머, 검증, UI 메시지처럼 변경 이유가 다른 로직이 한 함수나 훅에 섞이면 책임 단위로 분리합니다.
- R4. 긴 조건식, 매직 넘버, 반복되는 문구에는 이름을 붙입니다.
- 조건은 boolean 변수나 함수로 추출해 문장처럼 읽히게 하고, 시간/개수/제한값은 `ANIMATION_DELAY_MS`, `PAGE_SIZE`처럼 의미가 드러나는 상수로 둡니다.
- R5. 시점 이동을 최소화합니다.
- 핵심 플로우는 위에서 아래로 읽히게 배치하고, helper 함수는 핵심 플로우를 가리지 않도록 파일 하단이나 가까운 별도 파일로 분리합니다.
- 중첩 삼항 연산자는 피하고 명확한 변수, 조건 렌더링, 케이스 컴포넌트로 풉니다.

## Predictability

- P1. 같은 이름은 같은 동작을 해야 합니다.
- 기존 라이브러리나 모듈과 같은 이름의 래퍼를 만들지 않고, `apiClient`, `httpClient`처럼 역할이 드러나는 이름을 씁니다.
- P2. 같은 종류의 훅과 함수는 반환 형태를 통일합니다.
- `useXxxQuery` 계열은 TanStack Query의 반환 흐름을 크게 숨기지 않습니다.
- 검증 함수는 boolean과 객체 반환을 섞지 말고, 이유가 필요하면 `{ ok: true } | { ok: false; reason: string }`처럼 구분 가능한 타입을 씁니다.
- P3. 이름과 시그니처에 드러나지 않는 숨은 부수효과를 넣지 않습니다.
- storage write, navigation, analytics, logging이 필요하면 명시적인 함수나 옵션으로 분리합니다.
- API 함수는 원본 서버 응답을 가져오는 책임, 정규화 함수는 화면 타입으로 변환하는 책임을 분리합니다.
- 실패 가능성이 있는 로직은 빈 값, 로딩, 에러 상태를 호출부가 판단할 수 있게 만듭니다.

## Cohesion

- C1. 함께 바뀌는 코드는 가까이 둡니다.
- 기능 단위가 커지면 `features/<domain>/` 구조를 우선 검토하고, components, hooks, api, utils를 도메인 안에서 관리합니다.
- API 타입, API 요청 함수, 화면 전용 타입의 책임을 섞지 않습니다.
- C2. 함께 바뀌는 값은 한 곳에서 관리합니다.
- UI 문구, 기본 page size, sort key, TTL, 에러 메시지, 애니메이션 시간처럼 같이 바뀌는 값은 상수로 모읍니다.
- UI 애니메이션 시간과 이를 기다리는 delay 값처럼 서로 맞물린 값은 반드시 같은 기준에서 관리합니다.
- C3. 폼은 필드 단위 응집을 고려합니다.
- 입력, 검증, 메시지가 함께 바뀌는 경우 가까이 두고, 케이스가 갈라지면 무리한 공통화보다 분리를 선택합니다.

## Coupling

- U1. 영향 범위가 넓어지는 공통화는 기본적으로 금지합니다.
- 여러 화면에서 함께 바뀔지 확실하지 않은 컴포넌트는 섣불리 공통화하지 않습니다.
- 공통화 때문에 읽는 사람이 파일을 계속 오가야 한다면 중복을 허용합니다.
- U2. props drilling을 줄입니다.
- props가 3단계 이상 깊게 내려가거나 여러 갈래로 반복되면 composition, context, Zustand store, compound component 중 하나가 필요한지 검토합니다.
- U3. 책임 경계를 명확히 둡니다.
- API 통신은 api 모듈, 상태와 흐름은 hook 또는 view model, 순수 UI는 dumb component로 나누는 것을 우선 검토합니다.
- 컴포넌트가 API 원본 필드명에 직접 의존하지 않게 합니다.

## Frontend Defaults

- 사용자에게 보이는 문구는 한국어로 작성합니다.
- 누락 데이터는 요구사항 기준에 맞춰 `N/A` 또는 빈 상태로 표시합니다.
- 이미지에는 대체 텍스트를 둡니다.
- 버튼은 로딩/비활성 상태를 표현합니다.
- 카드 클릭 영역과 버튼 클릭 영역이 충돌하지 않도록 이벤트 경계를 분리합니다.

## PR Review Checklist

- 이 변경이 수정 또는 확장하기 쉬운가?
- 핵심 플로우가 위에서 아래로 읽히는가?
- 분기, 조건, 권한, 상태가 한 컴포넌트에 과하게 섞이지 않았는가?
- 이름, 반환 타입, 부수효과가 팀 규칙과 일치하는가?
- API 불확실성이 한 곳에서 관리되는가?
- 함께 바뀌는 값과 파일이 가까이 있고, 필요한 값이 SSOT로 관리되는가?
- 공통화가 영향 범위나 시점 이동을 키우지 않았는가?
- props drilling이 과하지 않은가?
- 로딩, 에러, 빈 상태가 있는가?
- 새 의존성이 정말 필요한가?
- 반응형에서 텍스트와 이미지가 깨지지 않는가?
- 변경 범위가 PR 목적과 맞는가?
- 공통화로 가독성이 떨어졌다면 PR에 이유와 근거를 남겼는가?
